# DDL 雷达

> 通知看得懂，事情不漏办。

面向大学生的校园通知行动助手：将竞赛、奖学金、考证和教务通知，整理成有原文依据、可人工确认、可跟踪进度的行动清单，并在截止前发送提醒。

## 当前状态

项目处于原型开发阶段。已实现 FastAPI 健康检查、MySQL 只读连接检查、LangChain 通知解析与原文引用匹配校验，以及 React 四页界面。

登录、事项总览和详情使用明确标注的演示数据；不提供真实认证，不保存任务进度。解析页已连接后端接口，但真实 DeepSeek 调用效果尚待验证。数据库保存、人工确认保存、通知对比、PDF 导入、站内与邮件提醒尚未实现。

下文“首版功能范围”等章节是目标设计，不代表功能全部完成。赛事要求和交付缺项见 [参赛清单](docs/submission/checklist.md)，启动步骤见 [复现指南](docs/reproduction/local-setup.md)，测试范围见 [验证记录](docs/testing/verification.md)。

## 解决的问题

- 通知篇幅长，报名资格、提交材料和截止时间容易遗漏。
- 看完通知后，仍需自己拆解准备步骤、安排任务。
- 补充通知修改要求后，难以识别哪些已有任务受到影响。
- 同时准备多个事项时，容易错过截止时间。

## 核心使用流程

导入通知 → 提取要求并展示原文依据 → 确认疑点 → 生成行动清单 → 跟踪进度与接收提醒 → 对比后续通知并确认调整。

例如：导入竞赛通知后，查看报名资格、提交材料、视频时长和截止时间；确认后生成代码仓库整理、Prompt 历史保存、演示视频制作等任务。收到补充通知时，查看要求变化和受影响任务。

## 首版功能范围

| 模块 | 计划功能 | 关键约束 |
| --- | --- | --- |
| 通知导入 | 粘贴文本、导入文字型 PDF | 保留原始内容、来源和导入时间 |
| 信息提取 | 提取事项、资格、材料、时间和提交方式 | 关键字段关联原文证据 |
| 疑点确认 | 标记信息缺失、条件不明和相互冲突的表述 | 未知信息不自动补全 |
| 行动清单 | 根据要求生成任务，支持用户增补和调整 | 区分原文要求、AI 建议和用户计划 |
| 进度管理 | 更新任务状态，查看材料准备进度和临期事项 | 数据持久化保存 |
| 通知更新 | 对比同一事项的新旧通知，展示受影响任务 | 用户确认后更新计划，保留历史版本 |
| 截止提醒 | 截止前 5 天、3 天、24 小时各提醒一次 | 站内消息和邮件提醒，支持关闭 |

### 原文证据

点击提取出的要求时，应能查看支持该结论的原文片段。没有明确依据的字段标记为“未说明”或“待确认”。

以下内容分别标注来源：

- **原文要求**：例如“提交 5—8 分钟演示视频”。
- **AI 建议**：例如“提前编写演示脚本”。
- **用户计划**：例如“周六完成录制”。

### 通知变更

系统展示变更前后的内容、各自依据及相关任务，不默认认定最新导入的文件具有更高效力。截止时间或要求存在冲突时，由用户确认采用的版本。

### 截止提醒规则

- 距离用户确认的截止时间剩余 5 天、3 天、24 小时时，各触发一次提醒。
- 提醒内容包括事项名称、截止时间、剩余时间和未完成任务。
- 站内消息保留提醒历史；邮件用于用户关闭网页后的通知。
- 事项完成或取消后，停止尚未发送的提醒。
- 用户确认新的截止时间后，取消旧时间对应的待发送提醒，并按新时间安排后续提醒。
- 导入时已临近截止，立即在页面提示，只安排未来的提醒，不集中补发已错过的节点。
- 已过截止时间的事项显示逾期状态，不安排截止前提醒。
- 通知只有日期而无具体时刻时，请用户确认用于提醒的时间，并标注该时间为用户设置。
- 首版界面使用北京时间（Asia/Shanghai），数据库统一保存 UTC 时间，避免依赖服务器所在时区。
- 保存提醒计划及各渠道发送状态；站内消息避免重复创建，邮件采用有限重试，并处理发送结果不明确的情况，降低重复发送风险。
- 网页关闭后邮件仍可发送，但后端、提醒进程及邮件服务需要持续可用。邮件可能因服务故障或收件方规则而延迟或投递失败。

### 首版暂不包含

截图 OCR、微信或教务系统自动抓取、自动报名、多人协作、复杂多 Agent 编排。日历导出等扩展功能待核心闭环完成后评估。

## 页面规划

1. **事项首页**：事项列表、临近截止提示、待确认内容和站内消息入口。
2. **通知解析页**：原文与提取结果对照，修改字段、查看证据和确认疑点。
3. **事项工作台**：要求、材料、任务进度、截止时间和提醒设置。
4. **通知对比页**：新旧通知差异、原文依据和任务调整确认。

## 技术方案

| 部分 | 选型 | 职责 |
| --- | --- | --- |
| 前端 | React + TypeScript | 页面交互、证据展示、任务与消息管理 |
| 后端 | FastAPI | 业务接口、输入校验、模型调用和数据访问 |
| 数据库 | MySQL | 保存事项、通知版本、证据、任务和提醒记录 |
| AI 编排 | LangChain | 通知解析、结构化输出和任务建议 |
| 提醒服务 | 独立调度进程 | 定期查询到期计划并处理发送任务 |
| 邮件服务 | SMTP | 发送截止提醒邮件 |

AI 负责理解与建议；程序负责数据校验、时间计算、状态流转和持久化；用户负责确认歧义、采纳建议和决定计划调整。提醒触发不依赖模型判断。

目前使用 DeepSeek OpenAI 兼容接口，模型标识为 `deepseek-flash`。依赖见 `backend/requirements.txt`、`backend/requirements.lock.txt` 和 `frontend/package-lock.json`。调度实现和部署方式待后续确认。

### 核心数据对象

- 事项：名称、状态、确认后的截止时间、提醒设置。
- 通知版本：原文、来源、导入时间及所属事项。
- 提取结果与证据：字段值、来源片段、确认状态。
- 待确认问题：冲突或缺失内容及用户处理结果。
- 任务：内容、来源、状态、计划时间及关联要求。
- 提醒计划与发送记录：提醒节点、通知渠道、发送状态和重试信息。

### 数据与配置约束

- 模型密钥、数据库密码和 SMTP 凭据仅在后端配置，不放入前端或提交到仓库。
- 对外提供服务前，需要完成用户身份与数据访问隔离；具体方案在实现前确定。
- 文档上传需要校验类型、大小和解析结果。
- 模型输出必须经过结构化校验；失败时保留输入并允许重试。
- 调用外部模型时会向所选服务发送必要的通知内容，界面需要说明；演示优先使用公开通知和虚构邮箱。

## 本地运行与 10 分钟复现目标

环境：Python 3.11、Node.js（当前构建验证使用 23.11.1）、npm、MySQL 8.0。正式交付前还需验证受支持的 Node LTS 环境与全新安装时间。

在项目根目录执行（已存在 `.env` 时不要覆盖）：

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.lock.txt
Copy-Item .env.example .env
cd backend
..\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

另开终端启动前端：

```powershell
cd D:\Chuanzhi_competion\frontend
npm ci
npm run dev
```

打开 http://127.0.0.1:5173，点击“进入演示工作空间”。未配置数据库或模型时，页面和 `/health` 仍可访问；真实解析需要在 `.env` 填写模型密钥。开发代理将 `/api` 转发到本机 8000 端口。

配置说明、接口样例、已知错误和不需密钥的测试方法见 [本地复现指南](docs/reproduction/local-setup.md)。尚未完成全新环境下的 10 分钟计时验证，不能声称已满足该交付目标。

## 验证计划

| 验证项 | 验收目标 |
| --- | --- |
| 要求提取 | 与人工整理的通知要求对照，记录遗漏与错误 |
| 证据引用 | 引用片段确实支持对应结论 |
| 歧义处理 | 缺失、冲突和模糊日期进入待确认流程 |
| 任务生成 | 原文要求、AI 建议和用户计划来源清楚 |
| 通知更新 | 正确展示变化，确认后调整相关任务 |
| 提醒时间 | 验证三个节点、临近导入、已逾期和时区边界 |
| 提醒状态 | 验证关闭、完成、取消、改期、重启与失败重试 |
| 持久化 | 刷新页面或重启服务后，记录仍然可用 |
| 故障处理 | PDF 解析、模型调用和邮件发送失败时有明确反馈 |

提醒逻辑使用可控时间验证，无需实际等待五天。真实邮件单独进行投递检查，逻辑测试不能代替实际投递验证。

计划邀请真实学生试用，记录任务完成情况、误解和操作障碍。测试结果和用户反馈以实际记录为准，未执行的验证明确标记为未执行。
